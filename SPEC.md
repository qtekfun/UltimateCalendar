# UltimateCalendar — Specification (SPEC)

Source: interview with the author (2026-10-06). What is not here is not invented: it is asked.

## 1. Goal

A beautiful Android calendar, with the interface of **Google Calendar** and the invitation management of **Apple Calendar**, for any account on the phone (Google, DAVx5, Nextcloud…) and, later on, with its own CalDAV connection. Free software (GPLv3), offline, no Google services, final destination F-Droid. Third app of the Ultimate family, next to [UltimateDeck](https://github.com/qtekfun/UltimateDeck) and [UltimateTasks](https://github.com/qtekfun/UltimateTasks).

### Problems it solves
- The free calendars (Etar, Fossify…) are functional but ugly and far from the Google Calendar experience.
- On Android there is no single place to see **all the invitations pending a reply**, from all accounts, like Apple's inbox.
- Reminders fail on phones from Chinese manufacturers (OPPO/ColorOS, vivo, Xiaomi, Honor): if the system puts the app to sleep or kills it, the reminder does not arrive and nobody notices.

## 2. Scope and assumptions
- **Data sources**, behind a single abstraction (`CalendarSource`):
  1. **Android calendar provider** (`CalendarContract`), read and write. It covers **Google** (the Google account already dumps its calendars there; neither Play Services nor any Google SDK is needed), **DAVx5** and any other account with a sync adapter. **This is the MVP.**
  2. **Own CalDAV** (Nextcloud as the reference), reusing the CalDAV client, the iCalendar reader/writer and the Login Flow v2 from UltimateTasks. **Post-MVP phase.**
- An event is always edited in its source of origin; the app does not copy events between sources.
- Reference volume: ~10 calendars, ~5,000 events in the provider, recurrences included. It must run smoothly with 20,000.
- `minSdk` 26, `targetSdk` the latest stable. Languages: English (default) and Spanish.

## 3. Functional requirements (v1)

### RF-01 First launch and wizard
Calendar permission (`READ_CALENDAR`/`WRITE_CALENDAR`), notifications, exact alarms and battery exemption; the manufacturer's autostart screens. It is the **UltimateTasks reliability wizard**, adapted, with a test reminder. If there is no account with calendars, it explains how to add Google or DAVx5 (and, when it exists, offers the own CalDAV connection).

### RF-02 Calendars and accounts
Google Calendar-style side drawer: calendars grouped by account, with their color, a visible/hidden checkbox and access to the calendar's settings (local name and color if the source does not allow changing them). Default calendar for new events.

### RF-03 Views
**Agenda** (continuous list), **Day**, **3 days**, **Week** and **Month**, like Google Calendar:
- Swipe sideways between periods; "Today" button; date picker from the header.
- All-day events in a top strip; overlapping events, in columns.
- Current-time line; device time zone, with an indication when an event has a different one.
- Tapping a free slot opens quick creation at that time; long-pressing an event lets you **move it and change its duration** by dragging (Day, 3 days and Week).
- Events with an unanswered invitation are drawn as in Google (outline, no fill).
- Material 3 with dynamic colors, dark mode and AMOLED. Tablet: adaptive layout.

### RF-04 Event detail
Title, date and time, all-day, time zone, repetition, place (opens the maps app via `geo:`), description, calendar, color, reminders, attendees with their status, organizer, video call links detected in place/description. Reply buttons if you are an invitee.

### RF-05 Create and edit events
- Fields: title, all-day, start/end, time zone, place, description, calendar, event color (if the source supports it), availability (busy/free), reminders (several).
- **Repetitions**: presets and custom (every N days/weeks/months/years, days of the week, "the 3rd Friday", end never/after N/until date). When editing or deleting a repetition: **only this event / this and following / all**.
- **Invite people**: add attendees by email (suggestions from contacts only if `READ_CONTACTS` is granted, optional). The one who sends the invitations is the source (Google, or the CalDAV server with server-side scheduling); the app does not send emails.
- Explicit saving ("Save"), with a warning on leaving if there are changes.

### RF-06 Pending invitations (Apple-style)
- A pending invitation is **any future event, in any calendar, visible or hidden, in which the user appears as an attendee and their status is "unanswered"** (`NEEDS-ACTION` / `ATTENDEE_STATUS_INVITED`). This is how Apple does it: it does not read a special inbox, it looks at the attendee status in all calendars. Since Google, Nextcloud (implicit scheduling) and DAVx5 leave the invitation in the calendar, it works the same for all accounts.
- "Me" is identified per calendar: the email of the account/calendar owner, plus aliases the user can add in Settings.
- **Invitations inbox**: icon with a counter in the top bar; list with Accept / Maybe / Decline, and open the detail.
- **Periodic check** every X (15 min by default; 15/30/60 min or manual only in Settings) with WorkManager, in addition to when opening the app, when pulling to refresh and when the provider reports changes (`ContentObserver`). Before searching, it asks the source to sync if possible.
- On replying, the attendee status is changed in the source; the source (Google, or the CalDAV server) sends the reply to the organizer.

### RF-07 Notifications
1. **New unanswered invitation** (always on by default): one notification per invitation, with Accept / Maybe / Decline actions. Several at once are grouped. An already-notified invitation is not notified again unless the organizer changes it.
2. **Changes and cancellations** of events you are attending (optional, off by default; can be turned on in Settings): change of date/time/place or cancellation by the organizer.
3. **Event reminders** (the event's `VALARM` alerts / `Reminders` rows), with Snooze (5 min / 15 min / 1 hour) and Dismiss actions, and "Open map"/"Join" if the event has a place or video call link.
- Separate notification channels for each type, so the user can adjust the sound in Android.
- If another calendar app on the phone also issues reminders, the wizard detects it and explains how to turn off its reminders so as not to receive them twice.

### RF-08 Reliability and recovery of missed reminders
Copy and adapt the UltimateTasks solution (T32–T34):
- **Local-only** reminders, no server: exact alarms (`USE_EXACT_ALARM` on Android 13+), optional alarm mode (`setAlarmClock`), rescheduling on boot, on app update, and on a change of time or time zone.
- **Recovery**: each shown reminder is recorded; if the app fell asleep or was killed and a reminder did not arrive, it is shown on return ("Did not arrive on time (10:30)") within a configurable window (6 / 24 / 48 h / never; 24 h by default), without an avalanche the first time. It runs on opening the app, after each periodic check, on every alarm and on every heartbeat.
- **Heartbeat**: exact alarm every 30 min while there are pending reminders, which recovers and reschedules.
- Optional **robust mode**: minimum-importance foreground service (`specialUse`).
- Wizard with per-manufacturer steps (OPPO/ColorOS, vivo, Xiaomi, Honor/Huawei, Samsung) and a test reminder.
- The same applies to invitation notifications: if the periodic check did not run, the next run notifies everything pending.

### RF-09 Search
By title, place, description and attendees, in all visible calendars.

### RF-10 Settings
Theme, first day of the week, initial view, default calendar, default duration, default reminders (with time and all-day), invitation check interval, own email aliases, notify changes/cancellations, recovery window, alarm mode, robust mode, wizard, version.

### RF-11 Encrypted backup
Copy from UltimateTasks: exports the settings (and, in the CalDAV phase, the optional session with password) encrypted with AES-GCM, restorable from Settings and from the first launch. This way the same configuration is carried to all phones. `allowBackup="false"`.

### RF-12 Own CalDAV (later phase)
Nextcloud Login Flow v2, discovery, `sync-collection`, events in Room as the source of truth, operation queue, conflicts, own recurrence engine with `RRULE`/`EXDATE`/`RDATE`/`RECURRENCE-ID`. Invitations and replies use server-side scheduling (RFC 6638). Same behavior as RF-03 to RF-11.

## 4. Out of scope (v1)
- Reading invitations from email (IMAP / `.ics` attachments): discarded by the author on 2026-10-06.
- Tasks (`VTODO`): they belong to UltimateTasks.
- Looking up other attendees' availability (free/busy).
- Any Google SDK, Play Services, Firebase, analytics or telemetry.

## 5. Synchronization and conflicts
- **Android provider**: syncing with the server is the job of each account's adapter (Google, DAVx5). The app writes as a normal client (without `CALLER_IS_SYNCADAPTER`), marks changes as dirty and lets the adapter upload them. It never deletes or modifies sync columns (`_SYNC_ID`, `SYNC_DATA*`) or foreign extended properties.
- **Own CalDAV**: same rules as UltimateTasks (Room as the source of truth, ETags, per-field conflicts with three-way merge, original `.ics` preserved and unknown properties intact).

## 6. Non-functional requirements
- Week view with 5,000 events: first draw < 300 ms on a mid-range phone; scrolling without jumps (reference profile in T-measurements).
- Battery: the periodic check queries only the local provider; it opens no network connections of its own (except in the CalDAV phase).
- Accessibility: `contentDescription`, 48 dp, font at 200 %, TalkBack in the agenda view and in the inbox.
- No personal data in logs.

### Measurements (T25)
**What was measured and how.** Three things, none on a phone: (1) JVM micro-benchmarks of the pure logic (`app/src/test/.../perf/DomainBenchmarksTest`, JUnit tag `benchmark`; `-PskipBenchmarks` excludes them) with data generated with a fixed seed (10 calendars, 5,000 and 20,000 events, 20 % recurring, 25 % with attendees) in two scenarios: *realistic* (events spread over two years, the visible month has 240 / 904) and *worst case* (all 5,000 / 20,000 within the visible range). They print `BENCH` lines and only assert very loose bounds (1 s realistic, 20 s worst case), meant to fail on an order-of-magnitude regression and not because of a slow runner. (2) `ProviderPerformanceTest` (instrumented, only with `perf=true`): seeds 5,000 and then 20,000 events with `applyBatch` in a LOCAL test account and measures `ProviderCalendarSource` over the real provider. It is launched with `gh workflow run ui-tests.yml -f perf=true` and the timings appear in the log (`T25 ...`) and in the `perf-timings-<api>` artifact (`gh run download`). It does not run in the nightly run. (3) Reading of the code of the hot paths and the periodic work.

**Limits.** GitHub Actions x86_64 emulator (API 26 and API 36, without GPU acceleration) and the CI/development machine: they serve to see orders of magnitude, linearity and regressions, they are **not** figures from a mid-range phone. They also do not measure Compose's first draw, scrolling or real battery consumption: that requires the author's phone (Macrobenchmark or `dumpsys batterystats`), and remains open.

**Provider results** (best of 5 reads except "first"; API 26 / API 36; 5,000 events | 20,000 events):

| Measurement | 5,000 | 20,000 |
|---|---|---|
| Month read (6-week grid), first time | 228 / 226 ms (2,048 instances) | 111 / 129 ms (8,640) |
| Month read, repeated | 17 / 41 ms | 94 / 125 ms |
| Laying out the month (`MonthLayout`, on ART) | 5 / 18 ms | 24 / 59 ms |
| Week read | 6 / 8 ms | 19 / 30 ms |
| Laying out the week (`TimeGridLayout`, on ART) | 5 / 16 ms (374) | 13 / 66 ms (1,590) |
| Search for a rare word (7 / 26 results) | 26 / 29 ms | 71 / 103 ms |
| Search for a word that almost all contain (4,406 / 17,549 results) | 785 / 1,630 ms | 3,257 / 6,099 ms |
| One-year read (the one from the invitation check; 30,349 / 124,955 instances) | 386 / 398 ms | 1,891 / 2,030 ms |
| `event(id)` (3 queries), average | 7.3 / 3.7 ms | 6.6 / 3.8 ms |
| Seeding (`applyBatch`) | 14 / 10 s | 70 / 59 s (cumulative) |

With the emulator data, reading and laying out a month or a week costs 30 to 200 ms at the worst volume, well below the 300 ms target (which also includes drawing, not yet measured). Everything grows linearly with volume: reading a range depends on the instances that fall in it, not on the total number of events.

**JVM results** (development machine with other builds running in parallel, so noisy; best of 7): `MonthLayout` 0.8 / 1.5 ms realistic and 13 / 65 ms with 5,000 / 20,000 instances in one month; `AgendaDays` 1.2 / 1.5 ms and 14 / 45 ms; `TimeGridLayout` for one week 0.7 / 0.7 ms and 17 / 62 ms; `OverlapLayout` 5,000 / 20,000 items in one day 34 / 353 ms (quadratic in the size of an overlapping group, irrelevant with the tens of events of a real day); `SearchMatcher` 144 / 614 ms over all events (≈ 30 µs per event); `RecurrenceEngine` 1,050 / 4,024 series 42 / 141 ms (only CalDAV will use it); `InvitationDetector.scan` 19 / 43 ms. No domain hot spot.

**Findings and fixes.**
- *Fixed:* `TimeGridViewModel` and `AgendaViewModel` laid out on the thread where the flow was collected (the main one), unlike `MonthViewModel`. They now use `flowOn(io)`. With the realistic volume it was ~1 ms, but with long agenda windows or very busy weeks it reached 50-60 ms.
- *Fixed:* with aliases configured, the invitation check read **all** the events of the next year one by one (each read is several queries to the provider: with 5,000 events that would be ~20-40 s of CPU every 15 min, with 20,000 more than a minute). Now the instance brings `hasAttendees` (`Instances.HAS_ATTENDEE_DATA`) and only the events that list attendees are read. Without aliases it already read only those with their own status.
- *Open, search:* the cost is linear in the number of **matches** (≈ 0.2-0.35 ms per event on the emulator, descriptions included): a query that almost all events satisfy takes 3-6 s with 20,000 events; real queries (infrequent words) take tens of ms. If needed: a limit or pagination of results, and not mapping the description of all candidates. `SearchRepository` also applies `SearchMatcher` again to what `ProviderCalendarSource.search` already filtered; it is a small duplication compared to the rest.
- *Open, recomposition:* reading the screens there are no clear problems (the month remembers `barsOn` and `fit` per week, the agenda uses item keys and `derivedStateOf`, the day/week grid only recomposes when the page changes). With Compose compiler 2.x (strong skipping enabled by default) models with `List` do not prevent skipping. It remains to confirm it with a profile on the phone.
- *Open, provider changes:* `source.changes` is conflated but not debounced: during a long sync each visible page re-reads its range. Measure on the phone with a real account before deciding whether an input debounce is needed (it would delay seeing one's own edit by 250 ms).

**Periodic-check battery (estimate from the code, not measured on a phone).** WorkManager with a 15 min period (the minimum allowed): 4 wake-ups/hour, 2 at 30 min and 1 at one hour; Doze groups and delays them. Each run makes one calendars query; one `Instances` read of one year (0.4 s with 5,000 events, 2 s with 20,000 on the emulator); N event reads (3 queries, 4-7 ms) with N = events with their own status, or with attendees if there are aliases; recovery of missed reminders (another 30-day read and of each event's reminders) and a Room write only if something changed. All of that is local. Each provider change while the process lives also triggers a check without syncing, with a 5 s debounce.

**Sync request (fix after T25).** What consumed the most was asking each non-LOCAL account, on every run, for a manual and urgent sync (`SYNC_EXTRAS_MANUAL` + `EXPEDITED`): it forced the Google/DAVx5 adapter to open the network 4 times per hour and account, with the system unable to group it. Now `SyncRequestPolicy` (in `sync/`, with an injected `Clock`) decides and `ThrottledSyncRequester` applies: (1) the periodic check and opening the app request a normal sync (without `MANUAL` or `EXPEDITED`), which the system can group; only "check now" (pull to refresh) requests it urgently; (2) per account, a background request at most every `max(interval, 30 min)` minus 5 min of periodic-work drift (so with 15 min one request is made every two runs, and with 30 min or 1 h, on every run); the time of the last request is stored in SharedPreferences (`sync_requests`) to survive process death; manual refresh has no limit; (3) in the background it is not requested if the provider says the account cannot be synced (`getIsSyncable == 0`), if it has calendar sync turned off (`getSyncAutomatically`, the `SYNC_EVENTS` switch), with battery saver on or without network; manual refresh only skips non-syncable accounts. In those cases the app relies on the `ContentObserver`: when the adapter (Google, DAVx5) writes new data, the provider notifies and a check is launched, so invitations keep appearing with the delay of the system's own sync and not that of the app. The scan does not change (T08: the notified mark is still replaced atomically at the end). The normal permissions `READ_SYNC_SETTINGS` and `ACCESS_NETWORK_STATE` are added, read-only, with no network access. **Expected sync wake-ups** per hour and account: from 4 urgent to 2 normal and groupable (15 or 30 min interval; 1 with 1 h), 0 with battery saver, without network or with calendar sync turned off. Local checks remain 4 per hour. *Deliberately not implemented:* skipping the run if nothing has changed would need a change marker that `CalendarContract` does not offer (a `ContentObserver` only works with the process alive, and comparing instance fingerprints would require persisting them and would not detect place changes of recurring events without re-reading them). **Recommendation:** measure 24 h on the author's phone with `adb shell dumpsys batterystats` and `Battery Historian` with 15 min and with "manual only", to confirm the effect of the fix.

**Pending on the author's phone:** first draw of the week with 5,000 events (< 300 ms), scrolling smoothness with Compose, battery consumption at 15 min, and the hypothesis about urgent syncs.

### Accessibility (T26)
**Verified (by code and by tests, without a real TalkBack):**
- A single pure descriptor, `domain.accessibility.EventSpeech`, says each event as a sentence ("title, from 9:00 to 9:30, place, calendar X, unanswered invitation, in the event's time zone: …") in grid blocks, all-day bars, Month chips, the day sheet, Agenda rows and search; and each Month cell as "Tuesday 6 October, 3 events". Words in `values/` and `values-es/` (with plurals), tested against the real XML in both languages.
- Color is never the only carrier: pending = outline, maybe = tint with border, declined = struck through and dimmed, and all three are spoken. The grid blocks used their own luminance threshold; they now use the shared `EventChip` colors, so the text reaches AA and declined events are struck through there too.
- Contrast: `ContrastAuditTest` runs through a grid of more than 200 calendar colors × 4 states × light/dark/AMOLED (text ≥ 4.5:1, outlines and dots ≥ 3:1) and the theme pairs (text, error/"now" line, primary/today, outline, dimmed days of the neighboring month). The dynamic colors from the wallpaper cannot be tested without a device.
- Font at 200 %: `DayBadge` no longer clips (the circle grows with the font and the Month reserves that height; if lanes do not fit it switches to dots), the hours column and the Agenda rows already scaled, calendar and account rows of the drawer have no line limit, the top bar title stops at 130 % (it shares a 64 dp row with five buttons; the reader says the whole title).
- TalkBack: headings marked (`heading()`), `stateDescription` on calendar visibility ("visible/hidden") and drawer accounts ("expanded/collapsed"), selection exposed in the editor's calendar and color selectors, inbox Accept/Maybe/Decline buttons with the event ("Accept: title") and the same three as custom actions on the card, empty state and skeleton as polite live regions, Material snackbars with a live region, the T18 TalkBack actions already existing, and the Create button with its own description collapsed or not.
- Motion: Agenda, Month and grid jump without sliding when the system removes animations (`rememberReduceMotion`); there is no flicker.
- Keyboard: IME actions in the editor, settings and search fields (Next/Done/Search); clickable elements use Material's focus indication.
- `AccessibilityAuditTest` (androidTest) walks the semantic tree of the main screens with data from the previews, at 100 % and 200 % font: no mute clickable nodes or ones under 48 dp, no repeated descriptions. It does not use Google's accessibility-test-framework: it would add 28 artifacts to dependency verification.

**Remaining exceptions (documented, not fixed):**
- Month chips (~20 dp), "+N" cells, timed blocks under 48 dp in Day/Week and narrow Week columns (7 days on a narrow phone) remain below 48 dp. Compose already enlarges the touch area of any clickable element up to 48 dp without changing the design (the nearest neighbor wins), a larger region is not added because it would overlap other events, and the full-size alternative path exists: tapping the day opens Day, "+N" opens a sheet with 48 dp rows and the Agenda lists everything with 48 dp rows.
- The "Today" icon has the number at a fixed size inside a 24 dp glyph (like any icon); its description says the date.
- Contrast of dynamic colors and of text pairs drawn by Material (menus, dialogs) is not measured here: Material is trusted.
- Numeric fields with an error are marked with color and `isError`, without their own supporting text.

**Only a real TalkBack session on the author's phone can confirm:** the reading order and focus after opening detail, editor, inbox and sheets; that the sentences sound natural in Spanish; that the custom actions (inbox, move/resize) appear in the actions menu; how long a dense Month day takes to read; the behavior with "Select to Speak" and with a physical keyboard/switch access; and the system font size at maximum on ColorOS (which can exceed 200 %).

## 7. Quality and CI
- `./gradlew check` green to close any task; CI requires it before merging (by convention: there is no ruleset enforcing it).
- Kover: ≥ 85 % over `domain`, `data` and `sync`; **100 %** in the invitation detector, the reminder scheduler, the recovery of missed reminders, the repetition split ("this and following") and, in the CalDAV phase, the queue, the resolver and the recurrence expansion.
- **Provider test harness**: a `CalendarSourceContract` contract suite that runs against `FakeCalendarSource` (unit tests) and against the emulator's real provider with a local test account (instrumented tests). Fixtures that reproduce the rows as written by **Google** and **DAVx5** (accounts, sync columns, attendees, repetition exceptions, extended properties). In the CalDAV phase, the same suite runs against the CalDAV source with MockWebServer.
- Manual releases with a `vX.Y.Z` tag and a workflow that builds and publishes the signed APK, like UltimateDeck (see `RELEASING.md`).

## 8. Known risks
- **Replying from the provider**: it must be verified that Google and DAVx5 upload the attendee status change and that the organizer receives the reply (Nextcloud does it on the server). Prototype in T02.
- **Inviting from the provider**: verify that Google and Nextcloud (via DAVx5) send the invitations when creating an event with attendees. T02.
- **Requesting sync from other accounts** (`ContentResolver.requestSync`): it may be limited by the system or by the adapter. If it is not possible, the real frequency depends on the adapter. T02.
- **Duplicate reminders** with the system calendar or other apps. RF-07.
- **Chinese manufacturers** that kill the app: mitigated by RF-08, measured on the author's phone.
- **Performance** of the week/month view with many recurrences: use the provider's `Instances` table, never expand in the UI.

## 9. Open decisions
- Should the "reminder already shown / invitation already notified" state be shared across phones (so as not to receive it on all of them) or is the settings copy enough? For now: local to each phone, as in UltimateTasks.
- Remind again about an unanswered invitation (e.g. 24 h before the event)? For now: no.
- Local name and color of read-only calendars: are they included in the backup?

### Decisions taken (interview 2026-10-06)
- Sources behind an abstraction: **Android provider first** (Google + DAVx5 + any account), **own CalDAV afterwards**. Google without Play Services.
- Apple-style invitations: attendee status in all calendars, check every X.
- Notify unanswered invitations always; changes and cancellations as an option.
- Recover missed reminders if the app fell asleep or was killed; **local-only** approach, no ntfy or server.
- MVP views: Agenda, Day, 3 days, Week, Month. Widget in another round.
- Editing MVP: events with reminders, repetitions and inviting people.
- Harness: fake provider + contract suite against the emulator's real provider.
- Releases with **release-please** (replaced on 2026-10-06 by manual releases with a tag, see below); F-Droid prepared from day 1 (reproducible, no prohibited dependencies, fastlane), submission to fdroiddata after 1.0, final versions only.
- At the end of the plan: icon, test-generated screenshots, header graphic and store texts.
- Force CI (the author had no preference; chosen): validated PR title, Claude Code hooks and UI tests on an emulator every night and on demand.
- 2026-10-06 (T00): `gradle/libs.versions.toml` starts with the UltimateTasks versions, without retrofit, okhttp or kotlinx-serialization (phase 6). detekt and ktlint are wired in already in T00 because the Claude Code hooks run them; the rest of the quality tooling (Kover, licensee, prohibited dependencies) is left to T01. `Random` is not copied from `TimeModule`: it is not used here.
- 2026-10-06 (T01): the 100 % packages are `domain.invitations`, `domain.reminders` (scheduler and recovery) and `domain.recurrence` (split); those of phase 6 are added with their code. `pr-title` allows a subject with an initial capital (Dependabot does not allow changing it).
- 2026-10-06 (T03): `Event.rrule` stores the raw RRULE so that rules not understood survive an edit; `RecurrenceRule.until` is date-only (inherited from UltimateTasks) and will have to be extended to date-time when the "this and following" split is done. All-day events are `LocalDate` with exclusive end, not instants. Ids as `value class` (`CalendarId`, `EventId`) over `Long`.
- 2026-10-06 (T04): `CalendarSource` contract: the instances of an all-day event are dated in UTC; every instance of a series, edited or not, carries `isRecurring = true`; attendees may come back in another order and with the organizer added; replying without being an attendee is `Invalid`. The fake only expands DAILY/WEEKLY rules with COUNT. Pending for T05: share `FakeCalendarSource` and `CalendarSourceContract` between `test` and `androidTest` (register an extra Kotlin source directory in `app/build.gradle.kts`, which was not done in T04) or copy them.
- 2026-10-06 (T07): `InvitationDetector(clock).scan(events, calendars, aliases)` and `diff(previous, scan)`. "Me" = the calendar's `ownerEmail` + aliases (only aliases if the calendar is not known). "Future" = starts after now in the clock's zone; an all-day event starts at midnight of that zone; a series that started in the past counts as future unless its UNTIL has passed. "Changed" = time, zone or place (empty = none). It stops being pending: cancelled if the event disappears or I am removed; answered elsewhere if my status is no longer `NEEDS_ACTION`; past events are ignored. The model has no event status, so "cancelled" is inferred from its disappearance. T08 persists `List<Invitation>`.
- 2026-10-06 (T02b, code): `ReminderEventSource` is a new interface, bound to an empty source until T04/T05 connect it. `ReminderSettingsSource` is also new and uses SharedPreferences: for now it only stores robust mode; the time of all-day reminders (09:00), the recovery window (24 h) and alarm mode use default values until the Settings task. Already-shown reminders are recorded in SharedPreferences, not in Room. An all-day event reminder fires at the configured time, `ceil(minutes/1440)` days before. It schedules 30 days ahead with a maximum of 200 alarms. Left out: snooze/dismiss, the test reminder and the per-manufacturer wizard. **Pending from the author:** measure on ColorOS with the app closed and the phone idle, and decide here which settings are needed.
- 2026-10-06 (T09): `RecurrenceRule.until` is now `Until.Day(date)` (all-day) or `Until.Moment(instant)` (timed); it is read and written as `UNTIL=yyyyMMdd` or `UNTIL=yyyyMMddTHHmmssZ`, and a floating time counts as its day. `RecurrenceSplitter.edit` and `.delete` receive the scope (only this / this and following / all) and return `CalendarResult<SeriesChange>` with `Update`, `Delete`, `ReplaceOccurrence`, `CancelOccurrence` and `Split(truncated, newSeries?)`. The cut ends the old series one second before the occurrence (UTC) if it is timed, or the previous day if it is all-day, and discards `COUNT`. `occurrencesBefore` is supplied by the caller (there is no expansion engine until T35) and carries over the `COUNT` if the rule does not change. "This and following" on the first occurrence becomes "all". A new series carries the id `RecurrenceSplitter.UNSAVED` (0). `CustomRepeat.toRule` takes an optional zone and `from` a required one, so that `UNTIL` is correct on timed events.
- 2026-10-06 (T06): `CalendarRepository` (`data/calendar`) offers `calendars()`, `visibleCalendars()`, `instances(range)` and `defaultCalendar()` as flows; they are re-read when `CalendarSource.changes` emits or the local settings change. ### Changes and cancellations of accepted events (RF-07 point 2, closes the audit gap)

- **What:** `InvitationChecker` follows, in the same pass as the pending invitations, the future events the user is attending (`ACCEPTED` or `TENTATIVE` as attendee, calendar with reply access or more, with other attendees and **not organized by the user**: a change of one's own is not an "organizer change"). It notifies through the "Changes" channel only with `notifyChanges` (date, time, zone or place) / `notifyCancellations` (deletion), both off by default. A pending invitation follows its T07 path (the states are disjoint: no double notices); on accepting it, it starts being followed silently.
- **Record:** Room table `attended_events` (schema 7, `Migration6To7`, with a migration test): key (calendar, event), start/end/zone (or days if all-day), **truncated SHA-256 hash of the place** (not the text), title (only to word "cancelled", when the event no longer exists in the source; same as `notified_invitations`) and the `ownEdit` mark. Never emails. It is replaced whole at the end of each successful check, after `notified_invitations` (idempotent notice: if the process dies between the two, the notice is repeated and replaced, not duplicated); that prunes past events. The first time it records without notifying.
- **Series:** the next occurrence (from `Instances`) is followed. If the followed one has already started, the next one is the new reference without notifying (the series advances). Moving an occurrence (or skipping the followed one) notifies as a change; a split series leaves the old one without future occurrences and the new one is seen for the first time, without notifying. Moving to the past, declining, leaving or going back to pending stops following it and deletes its notes (`ClearChanges`). An event that disappears notifies a cancellation just once, unless its calendar no longer exists (account removed: it is discarded without notifying).
- **Cost:** it reuses the events and instances that the check already reads (the candidates are those with `selfStatus`); it only reads separately, with `source.event`, the followed ones that no longer have an occurrence in the window (almost never), to distinguish "moved out of the window" from "deleted".
- **Own edits:** `OwnEditMarkingSource` wraps Hilt's `CalendarSource` and sets `ownEdit` in the record **before** `update`/`delete`/`editInstance`/`cancelInstance` (the provider reports the change instantly); if the write fails, it is unmarked. The next check takes the new state as the reference without notifying. *Known limitation:* a check that was already reading when the edit happened may replace the record without the mark and notify once about the own change.
- **Notice:** same channel and receivers as T21; tags `moved/<cal>/<ev>` and `cancelled/<cal>/<ev>` (ids only). Tapping the "moved" notice now opens the event detail (before, the inbox); the "cancelled" one opens the app (there is no detail). Coverage of `domain.invitations` at 100 % (line and branch). ### Review of the reply flow (2026-10-07)

The author tested 1.0.0-rc.1 with a Google account: on accepting from the notification, the invitation remains "awaiting reply" in Gmail. The app does not touch email (T42, parked); what makes Google consider it answered is that the reply reaches the organizer through Google's sync adapter. This review follows that chain link by link.

**Chain:** button → `InvitationActionReceiver` (`goAsync`) → `InvitationActionHandler` → `SourceInvitationResponses` → `CalendarSource.respond` → `ProviderCalendarSource` writes `Attendees.ATTENDEE_STATUS` of the own row → the Calendar Provider (not the app) derives `Events.SELF_ATTENDEE_STATUS` and sets `Events.DIRTY = 1` → the provider notifies Google's adapter → the adapter uploads the change and Google sends the reply to the organizer.

**What the provider does (knowledge of the AOSP code, confirmed on emulator).** AOSP's `EventInfoFragment.updateResponse` only updates (or inserts, if it does not exist) the owner's row in `Attendees`; it does not touch `Events`. `CalendarProvider2` does the rest when the writer is not an adapter: it marks the event `DIRTY` and recomputes `SELF_ATTENDEE_STATUS` by comparing the attendee's email with `Calendars.OWNER_ACCOUNT`. Therefore the app must not write `SELF_ATTENDEE_STATUS`, `DIRTY` or sync columns, and it does not (a test watches for this). On the emulator (LOCAL account) `ChainTest` checks, after pressing Accept on the real notification: `Attendees` row at ACCEPTED, `SELF_ATTENDEE_STATUS` at ACCEPTED, `DIRTY = 1` and `_SYNC_ID` unchanged. `DIRTY` only really matters in synced accounts; in LOCAL nobody uploads it.

**Series:** replying writes the master event's row, that is, to the whole series (this is how Google replies to an invitation from email, and it is what the app does; no exceptions are created). Replying to just one occurrence is not offered.

**Defects found and fixed**
1. `ProviderCalendarSource.respond` looked for the own row only with `Calendars.OWNER_ACCOUNT`, whereas the invitation detector, the detail and the inbox also use the Settings aliases. An invitation sent to an alias was seen, notified and always failed with "not sent" (`Invalid("not an attendee")`). Now the calendar owner, the account name if it is an address and the aliases (case-insensitive) are used. New unit test.
2. There was no retry: if the account could not sync at that moment (no network, "sync calendar" off, provider saying it does not sync), the reply stayed only in the provider and depended on it being synced someday. `ReplyRetryingSource` (wraps the source of all screens, notification included) schedules, if the account is in that situation, a single WorkManager job (`reply-sync`) that requires network, waits with exponential backoff (5 min) and gives up after 5 attempts, and requests an urgent sync (`SyncReason.MANUAL`). It survives process death. Battery saver mode does not count as "waiting" because the manual request is not held back.
3. The only message after replying from the notification was that it disappeared. Now a brief notice says "Accepted" / "Replied: maybe" / "Declined" and, if the account cannot sync now, adds that the reply will be sent when it syncs. It never says "sent": it only states what is known (saved on the phone).
4. After replying, the record of notified invitations and the "remind again" alarms were only updated when the provider's change notice reached a living process (with a 5 s delay). The receiver now launches a check without its own sync request when it finishes, which reconciles the record, removes the T40 alarms and brings the widgets up to date through the usual path.

**Reviewed and correct:** the receiver uses `goAsync` and finishes the result in `finally`; if the process dies between the tap and the write, the notification stays on screen and the button can be pressed again (replying twice with the same status is idempotent); a deleted event or one without access is `Gone` and removes the notification; revoked permission or provider error is `Failed` and leaves the notification with the "not sent" line (if the invitation never got recorded there is no line, it stays unchanged); inbox "Undo" is `respond(NEEDS_ACTION)` and is consistent. Own CalDAV: `respond` sets the own PARTSTAT and enqueues it, so it is not lost without network (the notice says it will be sent when the connection returns and the CalDAV job already retries); it does not use the Settings aliases (known limit).

**Pending / limits.** An own row is not inserted if it is missing: whoever is neither attendee nor organizer cannot reply (it is not an invitation for them and the detector does not offer it), the T04 contract remains `Invalid`. The urgent sync after each attendee write belongs to PR `fix/refresh-and-invitation-sync`; this review only adds the retry when that request could not be made. The inbox and detail messages do not distinguish "waiting for sync" (only the notification); the retry does cover all three paths.

**It can only be confirmed on the author's phone with a real Google account:** (a) that `DIRTY` reaches 1 and the adapter uploads the reply (look in `adb shell dumpsys content` or, easier, that the organizer receives "X has accepted" and that in calendar.google.com the attendee appears as "Yes"); (b) the state of the invitation card in Gmail (it may take a while or not update: that is email, out of scope, T42); (c) how long the reply takes to reach the organizer (seconds with urgent sync; in airplane mode, until the network returns and `reply-sync` runs); (d) an invitation sent to an alias.

### The invitation chain failed on the emulator (2026-10-07, `fix/invitation-chain-api36`)

`InvitationChainTest` failed intermittently (on the API 36 emulator; repeated in a single session, also on 26). **Cause (with the emulator log, not by assumption):** `InvitationCheckCoordinator` only checked when the `ContentObserver` heard a change, and the observer is registered asynchronously (`Dispatchers.Default`) a moment *after* the process starts. A write to the provider within that gap (the test seeds the invitation right after `startProcess()`) causes a change that nobody hears and there is no further check until the app is opened or the periodic work runs. The log showed `seeded` before `observer registered` in all the failed runs and no `onChange`. **Product bug, small:** a process that starts (e.g. woken by a sync adapter) could miss the change that woke it; the invitation appeared on the next periodic check. Changes that arrive *during* a check are not lost (`debounce` keeps the last one and checks it when finished; a test now covers it). **Fix:** the change watching begins with a check of its own (`onStart { emit(Unit) }`, with the same 5 s debounce and without requesting sync): one more local check per process start. **Measurement** (12 consecutive runs of the test in an emulator session, `ui-tests.yml` with `chain-repeats`): before, API 36 failed 10/12 and API 26 9/12; after the fix, 12/12 on API 36 and 12/12 on API 26. The workflow now uploads the emulator log (`ui-test-logcat-<api>`) and `tools/run-ui-tests.sh` allows repeating the chain. 1.0.0-rc.2 contains the gap.

### Invitations for each of my accounts (2026-10-07, `fix/own-accounts-invitations`)

The organizer row of my own account is never an invitation.
